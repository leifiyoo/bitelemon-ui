# Repository Instructions

These instructions apply to the entire repository.

## Current Migration Scope

The repository is being adapted from Watermelon UI into Bitelemon UI. The identity decision is recorded in `docs/rebrand/00-identity-and-decisions.md`; implementation must follow that decision and the numbered migration instructions.

- Do not modify application code, content, generated artifacts, deployment configuration, package metadata, assets, or tests for migration work until the relevant phase in `docs/rebrand/README.md` is active.
- Do not invent identity values beyond the approved decision document. Values marked as pending must not be used for production deployment or publishing.
- Preserve unrelated user changes in the worktree. Never reset or overwrite them.
- Use `docs/rebrand/README.md` as the execution index and the numbered documents as the migration instructions.

## Project Baseline

- Stack: React 19, TypeScript, Vite, Tailwind CSS 4, Motion, React Router, Bun.
- Source content is file-based and lives primarily under `src/data/contents`.
- Public routes are wired in `src/components/layout/app-routes.tsx`.
- The build generates sitemap, MCP catalog, operations metadata, and the shadcn registry before the Vite build.
- Preferred commands are `bun run lint`, `bun run build`, and the focused test commands documented in `docs/rebrand/05-migration-and-validation.md`.

## Naming And Branding Rules

Treat identity as typed data, not as a global search-and-replace operation.

- Platform identity includes visible names, canonical URLs, package names, CLI binaries, MCP keys, GitHub references, email addresses, SEO copy, plugin metadata, and infrastructure names.
- Content identity includes example prose, fictional company names, avatars, asset paths, filenames, component slugs, and user-facing installation commands. Classify each occurrence before changing it.
- Technical dependencies such as shadcn, Radix, Tailwind, React, Motion, and Cloudflare are not branding tokens. Keep them unless the approved migration explicitly replaces that technology.
- Keep old identifiers only where the approved compatibility matrix requires aliases, redirects, or deprecation notices.
- Never leave a stale old-domain URL in a canonical, installable, generated, or machine-readable surface.

## Content And UI Rules

- Preserve the existing content loader and colocated source-file pattern unless the approved content model explicitly changes it.
- Keep frontmatter slugs, folder names, route parameters, generated registry names, and installation IDs aligned.
- New object types require a documented schema, route behavior, metadata shape, loader behavior, sitemap behavior, registry/MCP behavior, and tests before implementation.
- Preserve responsive behavior, keyboard access, focus states, reduced-motion behavior, and source-backed previews while changing visual language.
- Do not rewrite demo copy or fictional data blindly. Decide whether it is product identity, sample data, attribution, or incidental prose.

## Generated Files

Do not hand-edit generated files when a generator is the source of truth. Update the generator or source inputs, then regenerate and review the result.

- `public/sitemap.xml` is generated by `scripts/generate-sitemap.ts`.
- `mcp/catalog.generated.ts` is generated by `scripts/generate-mcp-catalog.ts`.
- `src/data/ops.generated.ts` is generated by `scripts/generate-ops-manifest.ts`.
- `worker/routes.generated.ts` is generated route metadata and must remain consistent with the worker source.
- Registry JSON under `public/r/` and `public/registry/` is generated by `scripts/generate-shadcn-registry.ts`.

## Verification

Every implementation phase must include:

1. Typecheck, lint, focused tests, and a production build.
2. A search for old identity tokens in source, generated output, public metadata, package metadata, and deployment files.
3. Validation of every public URL, install command, route, API endpoint, MCP tool result, and plugin manifest affected by the change.
4. A mobile and desktop smoke test for changed pages.

If a check cannot run because a tool is unavailable, record the exact command, failure, and an equivalent fallback in the handoff. Do not claim a clean result without running it.
